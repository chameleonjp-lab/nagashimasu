## 1. エグゼクティブサマリー

「ナガシマス」は、8×8の土地を組み替え、予告された降雨を受け止め、居住区を守りながら安全な排水先へ水を導く、タッチ操作中心の治水パズルゲームである。

AQUAQUA／Wetrix系作品の核である「地形を作る → 雨を受ける → 水の流れを観察する → 漏水箇所を修理する」という循環を参考にする。ただし、名称、ロゴ、画像、音声、キャラクター、ステージ、ソースコード、固有の画面構成は利用せず、独自の世界観、ルール、UI、アート、実装で構築する。

初期版は、フル3Dや本格的な流体力学を採用しない。整数ベースの決定論的なグリッド水流シミュレーションと、Canvas 2Dによるアイソメトリック疑似3D表示を組み合わせる。これにより、iPhoneでの安定性、操作の分かりやすさ、再現可能なテスト、短い開発サイクルを優先する。

### 1.1 ゲームクリエイター検証の結論

初版は、技術設計、再現性、テスト、法務面が堅実である。一方、ゲームとしては次の危険が残っていた。

- 現在パーツを一方的に与える方式では、毎手の主体的な選択が弱い。
- 12秒経過時に仮置きを自動確定すると、タッチ操作の遅れをゲーム上の判断ミスとして扱ってしまう。
- 保護、貯水、排水、漏水、工事効率、スコアを同時に見せると、何を優先すべきか分かりにくい。
- 正確な水計算を作っても、水が動く快感、危機を切り抜ける達成感、失敗から学ぶ手応えが不足すると、治水シミュレーターに留まる。
- 6ステージを先に作ると、コアループが面白くないままコンテンツだけ増える危険がある。
- アイソメトリック盤面に対するタッチ選択、縦向き表示、確認操作の詳細が不足している。

この検証を受け、次を正式仕様へ変更する。

1. **現在／次パーツ方式を廃止し、2つの施工候補から1つを選ぶ方式にする。**
2. **キャンペーンの雨と施工候補は、原則としてステージごとの設計済み固定列にする。**
3. **時間切れ時の自動配置を廃止し、施工見送りとして扱う。**
4. **ステージ1・2は時間制限なしとし、以後段階的に緊張を上げる。設定で延長・無効化できる。**
5. **各ステージの主要目的は1つ、副目的は最大1つに制限する。**
6. **プレイ中に常時見せる主要指標は最大3つに制限する。**
7. **配置は選択と確定の2段階に分け、指を離しただけでは確定しない。**
8. **未来予測は次の1水流ステップまでに制限し、分かりやすさと考える余地を両立する。**
9. **安全排水、貯水成功、危機回避を明確な見せ場として演出する。**
10. **ステージ4以降を作る前に、縦切り版のゲーム性検証ゲートを設ける。**

## 2. 作品ビジョン

### 2.1 一文で表すゲーム

**次の雨を読み、2つの工事から1つを選び、水をため、そらし、安全に流して街を守る治水パズル。**

### 2.2 想定プレイヤー

- ルールが短時間で理解できるパズルを好む人
- 数分で遊べるが、繰り返すと効率化できるゲームを好む人
- 反射神経より、先読みと空間把握を使いたい人
- スマートフォンで片手または両手持ちの短時間プレイを行う人

専門的な治水知識は前提としない。ゲーム内の用語は、日常語として理解できる「上げる」「下げる」「ためる」「流す」「守る」を中心にする。

### 2.3 プレイヤーの基本動詞

1. **読む** — 次の雨、排水余力、危険な流向を見る。
2. **選ぶ** — 2つの施工候補から、今必要な方を選ぶ。
3. **組む** — 地形を上げる、下げる、流路を作る。
4. **ためる** — すぐ流すと危険な水を一時的に受け止める。
5. **流す** — 適切な時機に安全排水口へ導く。
6. **守る** — 居住区を浸水させず、被害を抑える。

### 2.4 プレイヤー体験の柱

#### 予測できる

次の2つの雨の位置、強さ、発生までの手数を見せる。失敗をランダム事故ではなく、読み違い、工事順序、排水能力の見落としとして理解できるようにする。

#### 選択に迷える

毎手、少なくとも次のどれかが競合する状態を作る。

- 今漏れそうな場所を直すか、次の雨へ備えるか。
- 水をすぐ流すか、一度ためて排水口の混雑を避けるか。
- 大きく地形を変えるか、少ない工事で高評価を狙うか。
- 便利な施工候補を今使うか、もう一方を残して次手へ備えるか。

#### 結果を理解できる

施工確定前に、変化するセル、高さ、次の1水流ステップの流向、危険度の増減を表示する。施工後は、何が原因で安全になったか、何が原因で漏れたかを短く示す。

#### 水を止めるだけでなく流す

高い壁で囲むだけでは最高評価を取れない。排水能力、貯水余力、将来の流路、工事量を同時に考え、水を安全に動かすことを中心にする。

#### 短時間でも起伏がある

1ステージ3～5分程度の中に、準備、最初の雨、立て直し、最大雨量、解決の流れを作る。常に同じテンションではなく、静かな計画と水が動く見せ場を交互に置く。

#### タッチ操作の失敗を理不尽にしない

大きな操作対象、選択と確定の分離、無効配置の非消費、明示的な施工見送り、ステージ中1回の完全Undoを用意する。

### 2.5 1手のコアループ

1. 次の雨と現在の危険箇所を見る。
2. 2つの施工候補を比較する。
3. 盤面へ仮置きし、回転・位置を調整する。
4. 次の1水流ステップの予測を見る。
5. 確定、取消、または施工見送りを選ぶ。
6. 雨が降り、水が動く様子を見る。
7. 安全排水、貯水、漏水、浸水の結果を確認する。
8. 次の雨に向けて判断を更新する。

この循環を「見る → 選ぶ → 試す → 決める → 見届ける → 学ぶ」として統一する。

### 2.6 ステージ全体のループ

1. 1画面の短いステージ目的を確認する。
2. ステージごとに設定された短い手数の治水工事を行う。
3. 最後の強雨を乗り切る。
4. 安全、工事効率、流量制御の3軸で結果を見る。
5. 次ステージへ進むか、より高い評価を狙って即再挑戦する。

### 2.7 独自化の中心

- エンドレスに耐えるだけでなく、目的の異なる短い治水ステージを攻略する。
- キャンペーンの雨と施工候補を設計済みの列にし、運より判断を評価する。
- 2つの施工候補から選ばせ、毎手の主体性を作る。
- 居住区保護、貯水、排水をステージごとに段階的に学ばせる。
- 水量と地形高だけでなく、危険な流向と排水能力超過を表示する。
- 一時貯水してピーク流量をずらす「ためてから流す」戦略を中心にする。
- 地形操作量が少ないほど高評価になる「工事効率」を導入する。
- 失敗直前の流れを短く再生し、次の挑戦へ知識を持ち越せるようにする。

### 2.8 アート・感情の方向性

写実的な災害表現ではなく、**卓上のミニチュア治水模型**を基本イメージにする。

- 地形は段差と等高線が読みやすい模型調。
- 建物、農地、排水設備は小さな立体記号として表現する。
- 保護できた街は明かりや旗で反応する。
- 安全排水が成功したときは、水路が一続きに光り、排水口が力強く作動する。
- 危険時は過剰な恐怖演出ではなく、模型上の警告灯、振動表現、流向矢印で示す。
- 水は盤面の中で最も鮮やかで、動きを追いやすい要素にする。

### 2.9 MVPで目指さないこと

- 元作品の完全再現
- 元作品のパーツ形状、演出、画面構成の模倣
- 高精度な流体力学シミュレーター
- フル3Dカメラ操作
- 大規模なオンラインサービス
- 長期運営を前提としたランキングやアカウント管理
- 多数の災害や設備を同時に覚えさせる複雑な経営ゲーム

## 3. コアルール

### 3.1 盤面

- 基本盤面は8×8の64セル。
- 各セルは最低限、次の状態を持つ。
  - 地形高さ
  - 水量
  - セル種別
  - 排水口フラグ
  - 保護対象フラグ
  - 漏水可能フラグ
  - 危険度
- 地形高さの初期範囲は0～6段を基準とする。
- 水量は整数単位で扱う。
- 斜面や水面の滑らかな見た目は描画側で補間し、ルール判定には使わない。
- 盤面の向きは固定し、ステージ中に回転させない。

### 3.2 セル種別

MVPでは次を使用する。

- 通常地面
- 保護対象地面
- 貯水対象地面
- 排水口
- 安全排水辺
- 危険な盤外流出辺
- 施工禁止セル

災害で壊れる地面、橋、ポンプ、門、水門などはMVP後の拡張対象とする。

### 3.3 地形と水の関係

- 地形を下げると、そのセルの貯水容量が増える。
- 水があるセルの地形を上げても、水量そのものは消えない。
- 水中で地形を上げると水面レベルが上がり、次の水流フェーズで周囲へ押し出される。
- 水中施工による押し出し方向は仮置き時に表示する。
- 地形上昇によって水を直接消去したり、安全排水扱いにしたりしない。
- 地形下降によって新たな穴を作っても、盤外漏水口にはならない。盤外漏水は辺またはステージ定義されたセルからのみ発生する。

この仕様により、浸水後も修理できる一方、目の前の水を無理に持ち上げると別方向へ被害が広がるリスクを作る。

### 3.4 施工候補

#### 2候補制

- 毎手、施工候補AとBの2つを表示する。
- プレイヤーはどちらか1つを選んで配置する。
- 使用しなかった候補は次の手へ残る。
- 使用した側だけが次の候補へ補充される。
- 施工見送りを選んだ場合、両候補は残り、雨と水流だけが進む。

この方式により、現在の危険へ対応するか、便利な候補を保存するかという判断を生む。

#### キャンペーンの候補列

- MVPの6ステージでは、施工候補の出現順をステージ設計データとして固定する。
- 同じステージは常に同じ条件で開始できる。
- ステージ内に必須の対処がある場合、その前に必要候補が最低1つは提示されるよう設計する。
- 同じ形状が3回以上連続しない。
- 一定区間内に上昇と下降の両方が含まれる。
- 片方の候補だけを選び続けても、常に有利にならないようにする。

シード付きランダム生成は、MVP後のチャレンジモード候補とする。ドメイン層では将来に備えてシード再現機構を保持する。

### 3.5 地形パーツ

MVPのパーツはデータ駆動で定義し、形状や効果量をコードへ直書きしない。

#### 上昇パーツ

- 単点1セル
- 直線2セル
- L字3セル

#### 下降パーツ

- 単点1セル
- 直線2セル

#### 共通仕様

- 効果量は基本1段。
- 回転は90度単位。
- 盤外、上限超過、下限超過、施工禁止セルへの配置は無効。
- 無効配置は手番、タイマー、Undo権を消費しない。
- 大きい形状は1手で広く変えられるが、不要なセルまで変える危険を持つ。
- 単点形状は精密だが、限られた手数を消費する。
- 大きいパーツが常に最適にならないよう、工事効率と地形への副作用を評価する。

形状数はプレイテスト用の初期値であり、意味の重複、選択の自明さ、視認性を検証して増減する。

### 3.6 セミリアルタイム進行

1手は次のフェーズで進む。

1. **状況確認フェーズ**  
   次の雨、現在の危険、ステージ目的を表示する。

2. **計画フェーズ**  
   2候補から1つを選び、位置と向きを決める。タイマーは操作可能になってから開始する。

3. **確認フェーズ**  
   変更セル、変更後の高さ、直近の雨、次の1水流ステップ、危険度変化を表示する。

4. **確定フェーズ**  
   確定、取消、施工見送りのいずれかを選ぶ。

5. **降雨フェーズ**  
   発生条件を満たした雨イベントを適用する。

6. **水流フェーズ**  
   水流シミュレーションを複数固定ステップ進め、アニメーションで変化を示す。初期値は1手あたり4ステップ、調整範囲は2～6ステップとする。

7. **評価フェーズ**  
   漏水、排水、浸水、保護対象、クリア、失敗を評価する。

#### タイマー原則

- ステージ1・2は時間制限なし。
- ステージ3以降で段階的に時間制限を導入する。
- 雨、水流、結果表示、チュートリアル中はタイマーを停止する。
- 残り3秒で視覚的な警告を行う。
- 時間切れ時は、仮置きが存在していても自動確定しない。
- 時間切れは施工見送りとして扱い、雨と水流が進む。
- 設定から思考時間を標準、長め、無制限に変更できる。
- 思考時間の変更によってステージ進行や評価上限を制限しない。
- ゲームの難しさはタイマーだけに依存させない。

### 3.7 雨予報

- 常に次の2つの雨イベントを表示する。
- 表示内容は、範囲、強度、発生までの手数。
- 雨範囲は盤面上の模様、輪郭、アニメーションで表示する。
- 色だけで雨の強弱を区別しない。
- キャンペーンの雨イベントはステージごとの設計済み固定列を使用する。
- 雨の形状は、単点、直線、2×2、十字など少数から始める。
- 予報表示と実際の降雨セルを完全に一致させる。
- 雨が強まる場合は、単に数値を増やすだけでなく、範囲または連続回数の変化としても理解できるようにする。

### 3.8 配置プレビュー

仮置き時に、次だけを確定情報として表示する。

- 変更対象セル
- 変更後の地形高さ
- 水中施工で押し出される可能性
- この手で雨が降る場合の降雨範囲
- 施工後、降雨後の**次の1水流ステップ**
- 危険度が上がるセルと下がるセル
- 排水口の能力超過見込み

2ステップ先以降、次々回の雨、ステージ終了までの未来は自動計算して見せない。完全な未来を表示すると、プレイヤーが考える余地を奪い、毎手プレビューを総当たりする作業になるためである。

プレビューには「次の1歩」という明確なラベルを付け、長期予測ではないことを伝える。

### 3.9 水流

MVPでは上下左右の4近傍のみを使用する。

各セルの水面レベルを次で定義する。

`水面レベル = 地形高さ × 高さ係数 + 水量`

1回の固定ステップでは次を行う。

1. 現在セルと上下左右の水面レベルを比較する。
2. 現在セルより低い隣接先を抽出する。
3. 移動可能量を、現在水量、勾配、1ステップ上限から決定する。
4. 移動量を差分バッファへ記録する。
5. 全セルの計算後に差分を一括反映する。
6. 排水口へ入った水と盤外へ漏れた水を別々に集計する。

計算中に隣接セルを直接更新しない。これにより、セルを走査する順番で結果が変わる問題を防ぐ。

複数の隣接先が同じ最低水面の場合は均等分配し、整数除算の余りはセル番号と水流ステップから決定する循環順で配る。常に同じ方向を優先する偏りを抑えながら、結果の再現性を維持する。

MVPでは蒸発、浸透、波、飛沫の物理判定を扱わない。必要な見た目は表示演出として実装する。描画上の水が斜めに見えても、ルール上は上下左右にしか移動しないことを矢印とセル強調で誤解なく示す。

### 3.10 排水、漏水、浸水、貯水

- **安全排水:** 指定された排水口または安全辺へ流れた水。プラス評価。
- **漏水:** 危険な盤外辺へ流出した水。被害ゲージとマイナス評価へ加算。
- **浸水:** 保護対象セルの許容量を超えた水。重大なマイナス評価。
- **貯水:** 指定された貯水セルまたは地形内に一時的に残した水。ステージ目的に応じて評価。

排水口には1水流ステップあたりの処理能力を設定する。処理能力を超えた水は滞留し、周囲へあふれる可能性がある。

浸水は保護対象へ生じた被害の読み取り値であり、水を盤面から除く処理ではない。浸水した水は盤面に残し、後続の水流と施工へ影響する。水量収支は`初期水量 + 追加雨量 = 盤面残量 + 安全排水 + 漏水`で検査し、浸水量を重ねて足さない。M1の詳細な計算順と初期係数は`docs/adr/0001-deterministic-water-model.md`を正本とする。

排水口の表示には「流入見込み／処理能力」を図形で示し、数字だけを読まなくても混雑を理解できるようにする。

### 3.11 ゲーム性を作る3つの競合

#### 応急処置と将来準備

今漏れそうな場所を直すほど、次の大雨への準備が遅れる。次の2つの予報を見て、どこまで先回りするかを判断させる。

#### 貯水と排水

すぐ排水口へ集中させると処理能力を超える。安全な窪地へ一時貯水し、後の下降パーツで流路を開く選択を作る。

#### 安全と工事効率

多数のセルを高くすればクリアしやすいが、高評価は取りにくい。初回クリアでは安全を優先でき、再挑戦では少ない工事で解けるようにする。

### 3.12 危険度表示

危険度は内部物理を隠す曖昧な総合点ではなく、理由を説明できる警告とする。

最低限、次を反映する。

- 盤外または保護対象へ向かう水の勾配
- 現在水量
- 周囲の堤防余裕
- 次回雨量
- 排水口までの経路
- 排水能力の超過見込み

表示段階は「安全」「注意」「危険」「決壊寸前」の4段階を基準とし、色、輪郭、模様、矢印を併用する。

危険セルを選択した場合、次のような短い理由を1つまたは2つ表示する。

- 「次の雨で水位が堤防を1段超えます」
- 「排水口の処理量を2超えます」
- 「住宅側が最も低くなっています」
- 「この水路は途中で行き止まりです」

### 3.13 Undo

- 1ステージにつき1回だけ使用できる。
- 直前の有効な配置または施工見送り1手を完全に取り消す。
- 次の施工確定前まで使用できる。
- 地形だけでなく、次をすべて復元する。
  - 地形
  - 水量
  - 排水量
  - 漏水量
  - 浸水量
  - 評価値
  - 手数
  - 施工候補A／B
  - 候補列の位置
  - 雨イベントキュー
  - 乱数状態
  - 勝敗状態
- 無効操作、候補選択、回転、仮置き、取消には消費しない。
- Undo後は、どの危険がどう戻ったかを短くアニメーション表示する。

### 3.14 ステージ目的の階層

各ステージは、常に次の構造にする。

- **主要目的:** 1つだけ。クリアに必須。
- **副目的:** 最大1つ。高評価または追加学習に使用。
- **失敗条件:** 最大2つ。常時確認できる。

例:

- 主要目的: 「住宅を最後の雨まで守る」
- 副目的: 「安全排水を20以上行う」
- 失敗条件: 「住宅被害3」「漏水ゲージ満杯」

プレイ中に複数のスコア内訳を常時見せず、今の目的と危険を優先して表示する。

### 3.15 MVPステージ構成

数値はプロトタイプ検証用の初期値であり、プレイテストで調整する。

| ステージ | 仮称 | 手数目安 | 標準タイマー | 主要学習・目的 | 初見クリア率目標 |
|---|---|---:|---:|---|---:|
| 1 | はじめの池 | 3 | なし | 上昇パーツで堤防を作り、指定量を貯水する | 90～100% |
| 2 | 海へひらく道 | 3 | なし | 下降パーツで水路を作り、安全排水口へ導く | 80～100% |
| 3 | 雨雲の順番 | 4 | 20秒 | 2つの雨予報を読み、住宅浸水を防ぐ | 60～85% |
| 4 | 細い排水口 | 11 | 18秒 | 排水能力を理解し、流れを複数経路へ分散する | 45～75% |
| 5 | ためてから流す | 12 | 15秒 | 一時貯水でピーク流量をずらし、後から流す | 35～65% |
| 6 | ナガシマス | 13 | 12秒 | 上昇、下降、予報、貯水、分散排水を統合する | 25～55% |

ステージ1〜3は、最短解の後に意味のない施工見送りが続かないよう、手数と雨の間隔を短くした画面なし検証用の値である。ステージ1・2は2回目の雨を3手目までに、ステージ3は3回の雨を2〜4手目に置く。ステージ2の安全排水目標は、短い雨列で達成できる8へ合わせている。これは水流の規則や評価式を変える調整ではなく、候補選択と雨予報の判断を残すためのステージデータ調整である。

各ステージは次の感情曲線を持つ。

1. **準備:** 2～3手。盤面を読み、最初の方針を決める。
2. **最初の試験:** 弱い雨で、地形の狙いが機能するか確認する。
3. **立て直し:** 問題箇所を修正する余地を与える。
4. **最大雨量:** ステージ固有の判断を要求する。
5. **解決:** 最後の水が安全に流れ、結果が見える。

ステージ3以降は、最低2つの有効なクリア方針を持たせる。ステージ6では、少なくとも2つのS評価候補ルートを確認する。

### 3.16 スコアと評価

クリア判定と評価を分離する。低評価でも主要目的を達成すれば次へ進める。

結果画面では次の3軸だけを表示する。

1. **安全:** 漏水、浸水、保護対象の状態。
2. **工事効率:** 変更セル数、不要な地形変更、残り手数。
3. **流量制御:** 安全排水、排水能力超過、一時貯水の使い方。

初期配点の目安は、安全50、工事効率30、流量制御20とする。閾値と配点はデータ化し、プレイテストで調整する。

- S／A／B／Cの4段階を基準とする。
- 思考時間の長短は直接スコアへ加えない。
- 未使用Undoは小さな補助評価に留める。
- 初回プレイ中は生の総合点を強調せず、目的達成と危険状態を優先する。
- 結果画面では「次に改善する1点」を明示する。

### 3.17 水が動く面白さ

水流は待ち時間ではなく、施工の答え合わせと見せ場にする。

- 3セル以上を通って安全排水できた場合、流路を一続きに強調する。
- 排水能力を超えずに大量排水できた場合、「安全に流せた」ことを明確に祝う。
- 一時貯水池が狙いどおり満ちた場合、容量が機能したことを表示する。
- 決壊寸前から安全域へ戻した場合、警告灯が消え、街が反応する。
- スコア表示だけでなく、盤面上の水、建物、排水設備で結果を伝える。

連続排水を独立した複雑なコンボルールにはしない。まずは視覚・音・短い加点表示による達成感として実装する。

### 3.18 失敗と再挑戦

失敗時は、情報量を増やしすぎず次を示す。

1. 最初に破綻した場所。
2. 破綻の主原因を1文。
3. 最後の約3秒または最後の1水流フェーズの短い再生。
4. 「ここを1段上げる」「排水を分散する」など、次の挑戦へつながる1つのヒント。
5. 1タップで同条件から再挑戦。

再挑戦時は説明画面を再度強制表示しない。必要な場合だけ開けるようにする。

### 3.19 支配戦略の禁止

次の単純戦略を自動または手動で試し、複数ステージを高評価で突破できないことを確認する。

- 外周をひたすら上げる。
- 排水口まで最短距離をひたすら下げる。
- 常に大きいパーツを選ぶ。
- 常に上昇パーツだけを選ぶ。
- 雨予報を無視して現在の漏水だけを直す。
- 毎手施工見送りを選ぶ。
- 片方の施工候補だけを選び続ける。

同じ単純戦略で4ステージ以上をA評価以上で突破できる場合、ステージ設計または評価設計を修正する。

### 3.20 チュートリアル原則

- 1回に教える新概念は1つ。
- 1つの説明は原則2行以内。
- 新概念を教える間はタイマーを停止する。
- 説明後、実際に対象操作を行うまで次へ進めない。
- 誤った操作を禁止するだけでなく、なぜ無効かを短く示す。
- ステージ1では「上げる」「確定」「水が低い方へ流れる」だけを教える。
- ステージ2で「下げる」「排水」を教える。
- ステージ3で初めて「2つの雨予報」とタイマーを教える。
- ステージ4で「排水能力」を教える。
- ステージ5で「ためてから流す」を教える。

## 4. UI・操作計画

### 4.1 画面向き

横向きを最も見やすい正規レイアウトとするが、縦向きも実際にプレイ可能にする。

#### 横向き

- 中央: 8×8アイソメトリック盤面
- 左: 主要目的、次の雨、残り手数
- 右: 施工候補A／B、回転、確定、取消、Undo、施工見送り
- 上部: 最大3つの主要指標
- 下部: 危険理由または短いチュートリアル

#### 縦向き

- 上側: 盤面
- 下側: 施工候補と操作をまとめたボトムシート
- 主要目的と雨予報は盤面上部に固定
- 盤面を単純に縮小してタップ領域を失わない
- 情報パネルは折りたたみ、盤面と主要操作を優先する

横向きを推奨する案内は表示できるが、縦向きで操作不能にはしない。

### 4.2 カメラ

- MVPではカメラ角度を固定する。
- ピンチズーム、二本指回転、自由パンを実装しない。
- 盤面全体を常に確認できる大きさにする。
- 地形が高くなっても奥側セルが完全に隠れない投影と高さ倍率を使う。
- 選択セルは前面へ輪郭表示し、地形側面に隠れても位置が分かるようにする。

### 4.3 配置操作

1. 施工候補AまたはBをタップする。
2. 盤面セルをタップしてアンカー位置を選ぶ。
3. 必要ならドラッグして位置を調整する。
4. 回転ボタンで向きを変える。
5. 確定ボタンで施工する。
6. 取消ボタンで仮置きを解除する。
7. 施工したくない場合は施工見送りを選ぶ。

#### 誤操作防止

- 指を離しただけでは確定しない。
- 同じセルを再タップしても自動確定しない。
- ドラッグ中の仮置き表示は、指の24～32 CSS px上へずらして見えるようにする。
- ドラッグ終了後も仮置き状態を保持する。
- 無効位置では確定ボタンを無効化し、理由を表示する。
- 雨・水流アニメーション中は盤面入力をロックする。
- 入力ロック中も一時停止と設定は利用できる。
- 連打で同じ施工が二重確定しない。

### 4.4 セル選択

- アイソメトリック上面のポリゴンでヒットテストする。
- 境界付近では最も近いセル中心へ補正する。
- 補正後の選択セルを必ず仮置き表示で確認させる。
- 見た目上のセルが44 CSS px未満でも、選択と確定を分けて誤配置率を下げる。
- 奥側セルを選ぶとき、手前の地形側面を誤って選ばないよう上面優先判定を行う。

### 4.5 HUDの情報階層

プレイ中に常時見せる主要情報は最大3つにする。

1. 主要目的の進捗
2. 被害または漏水の危険
3. 次の雨までの手数

次の情報は必要時に見せる。

- 排水量の詳細
- 工事効率
- 水量の正確な数値
- 評価予測
- セルごとの危険理由

施工候補と雨予報は、数値メーターではなく選択に必要なカード・図として表示する。

### 4.6 分かりやすさ

- 地形高さは段差、影、等高線で示す。
- 水深は水面高と濃淡で示す。
- 上昇と下降は色だけでなく、上向き／下向き形状で示す。
- 雨予報、現在水、水流予測を異なる模様にする。
- 安全排水と危険漏水は異なる出口形状とアニメーションにする。
- 保護対象は盤面上で常に識別できる。
- セル選択時に「地形3・水2」のような簡潔な情報を表示できる。
- 盤面上の矢印は重要な流向だけに絞り、全セルへ常時表示しない。

### 4.7 ターンのテンポ

非操作時間が長くならないよう、初期目安を次とする。

- 地形変形: 180～250ms
- 雨: 250～400ms
- 水流: 600～900ms
- 評価表示: 150～250ms
- 1手の非操作時間合計: 原則1.5秒以内

ステージ2クリア後は、水流再生速度を標準／高速から選べるようにする。高速でも最初の漏水、浸水、排水能力超過は省略せず強調する。

### 4.8 アクセシビリティ

- 主要タップ領域は44 CSS px以上。
- 色だけに依存しない。
- 主要ボタンに文字ラベルを付ける。
- `aria-label`を適切に設定する。
- 音なしで全情報を理解できる。
- アニメーション削減設定を尊重する。
- 思考時間を延長または無制限にできる。
- 強い点滅を使用しない。
- 横スクロール、長押しメニュー、ページの誤スクロールを防ぐ。
- ピンチズームをゲーム操作として使用しない。

### 4.9 音

MVPのロジック完成までは音を必須にしない。追加時は次を守る。

- 初期設定は無音。
- ユーザー操作で有効化できる。
- 配置、雨、安全排水、漏水、浸水、危機回避、クリア、失敗で役割を分ける。
- 安全排水は明るく短い音、漏水は低く明確な警告音にする。
- 同時に多数の水音を鳴らさず、イベント単位でまとめる。
- 音がなくても全情報を理解できる。

## 5. 技術選定

### 5.1 採用技術

| 領域 | 技術 | 採用理由 |
|---|---|---|
| 言語 | TypeScript | 状態構造とルールの型安全性、リファクタリング、テスト容易性 |

| 水流 | 独自の整数セル方式 | 決定論、再現性、テスト容易性、低負荷 |
| 状態配列 | TypedArray | 固定盤面、予測可能なメモリ、スナップショット容易性 |
| 単体テスト | Vitest | TypeScript／Viteとの統合 |
| E2E | Playwright | ChromiumとWebKitで主要フローを検証 |
| 保存 | localStorage | MVPにサーバー不要 |
| 配信 | GitHub Pages | 静的配信で無料運用可能 |

### 5.2 MVPで採用しない技術

- Phaser
- PixiJS
- Three.js
- WebGLによるGPU流体演算
- WebGPU
- 物理エンジン
- Supabase
- サーバーレス関数
- ログイン
- オンラインランキング

描画表現がCanvas 2Dの限界に達した場合でも、ゲームロジックを描画から分離し、表示層だけをPixiJSまたはThree.jsへ交換できる構成にする。

### 6.4 決定論

同じステージデータ、設定、操作列から同じ結果を得ることを必須とする。

- ゲーム判定に`Math.random()`を直接使用しない。
- 水流を描画フレーム時間へ依存させない。
- 浮動小数点値を勝敗判定へ使用しない。
- タイマー切れは「施工見送り・タイムアウト」として操作ログへ記録する。
- 施工候補列と雨列をステージデータに含める。
- 操作ログからゲーム全体を再生できる構造にする。

### 6.5 Undo実装

MVPの盤面は小さいため、複雑な差分圧縮より安全性を優先し、直前手の完全スナップショットを保持する。

- TypedArrayを複製
- スカラー状態をコピー
- 雨キューをコピー
- 候補A／Bと候補列位置をコピー

- タイマー結果をコピー

64セル規模ではメモリ負荷は無視でき、復元漏れのリスクを下げられる。

### 6.6 保存

localStorageには次だけを保存する。

- 設定
- クリア済みステージ
- 最高評価
- チュートリアル既読状態
- 必要に応じて中断中ステージ

保存データへスキーマバージョンとステージデータ版を付ける。破損または互換性不一致時はゲーム全体を停止させず、安全に初期化できるようにする。

現時点では、ステージ3の標準20秒、長め設定、無制限設定をApplication側の壁時計タイマーとして実装している。雨・水流・結果の再生中はタイマーを止め、手番の待機へ戻ったときだけ次のタイマーを開始する。手動一時停止とPage Visibilityによる自動一時停止は同じ残り時間を共有し、復帰時に残り時間から再開する。時間切れはStageSessionの明示的な`timeout`操作として一度だけ送る。

設定、チュートリアル既読、最後に選んだステージ、クリア済みステージの最高点は、版付きのlocalStorage値へ保存する。受理済みの高レベル操作列はStageSaveV1として別キーへ保存し、リロード時に同じStageReplayを再実行してfullStateHashとreversibleGameplayHashを照合する。壁時計の経過時間、仮置き中の配置、再生演出の位置は保存しない。保存値が壊れている場合、定義の版・digestが一致しない場合、または復元後のハッシュが一致しない場合は保存を破棄し、初期状態でゲームを開始できる。

途中保存は受理済み操作の直後に更新し、タイトル画面の「続きから再開」から明示的に再開する。同じステージを「このステージを始める」で新規開始した場合は、そのステージの保存を破棄する。クリアまたは失敗の再生が終わった時点で途中保存を破棄するため、終端状態を途中再開として残さない。復元時にも終端状態を再開不可として扱い、手作業で作られた保存値が残っていても新規開始へ戻す。

チュートリアルは初回または未確認時に開いた状態で表示し、閉じる操作またはステージ開始で既読として保存する。既読後もタイトル画面の「遊び方を表示」から再び開ける。

確定後の基本演出は、StageSessionのtraceに含まれる施工セル、雨セル、水流結果をPresentation側で短く脈動させる。水量や流向を再計算せず、再生中の入力ロックと決定論的なルール実行を維持する。演出用の進行値は各trace区間内で0から1へ正規化し、盤面状態やリプレイ記録には保存しない。

端末が`prefers-reduced-motion: reduce`を示す場合は、同じ強調を固定表示へ切り替え、脈動だけを止める。施工・雨・水流の順序、状態表示、入力ロックは通常時と同じにする。

ステージ2をクリアした後は、タイトル画面で水流再生速度を標準／高速から選べる。高速はPresentationのtrace区間を短くするだけで、施工・雨・各水流step・評価の表示を省略しない。速度設定はスコア、クリア判定、タイマー、操作ログへ影響させず、版付き進捗保存v2へ保存する。既存の進捗保存v1は標準速度として読み込む。

結果画面では、StageSessionが保持する失敗理由と保護セル別の初回浸水情報を使い、最初に確認すべき破綻箇所と原因を短く表示する。失敗理由に対応する行動を1つだけ「次に改善する1点」として示し、クリア時は未最大の評価軸から改善点を選ぶ。これはPresentation側の変換であり、水流再計算、スコア変更、追加のランダム要素は行わない。危険側の正確なセルがDomainに記録されていない場合は、危険側の出口という粒度に留めて推測しない。

タイトル画面のステージ選択では、ステージ1を常に開き、ステージ1のクリア記録があるとステージ2、ステージ2のクリア記録があるとステージ3を開く。未解放ステージは選べないことと、何をクリアすれば開くかをカード上に表示する。既存保存にステージ2または3のクリア記録がある場合は、その記録を尊重して該当ステージを開く。解放状態は既存のクリア記録から表示時に計算し、新しい保存形式やDomain状態は追加しない。

- 同じ入力は同じ結果になる。
- Undo後のハッシュが操作前と一致する。
- 水流ステップを繰り返しても異常状態がない。

### 10.3 統合テスト

- 1手の全フェーズ
- 2候補選択から補充まで
- 雨予報から降雨まで
- 配置から水流・評価まで
- 1ステッププレビューと実結果の一致
- タイムアウト時の施工見送り
- 一時停止・再開
- ステージクリア
- ステージ失敗
- 失敗再生
- 保存・読込
- バージョン移行

### 10.4 E2E

- タイトル → ステージ選択 → プレイ → 結果
- 候補A／B選択

### 10.5 ゲーム性テスト

- 主要目的を30秒以内に理解できるか。
- 施工候補A／Bの違いが意味のある選択になっているか。
- 仮置き予測を見ずに適当に置く行動と、予測して置く行動に結果差があるか。
- 雨予報を読む価値があるか。
- 安全排水と一時貯水の両方に出番があるか。
- 大型パーツが常に最適ではないか。
- 最初の失敗から次の改善点を説明できるか。
- 水が動く時間を待ち時間ではなく答え合わせとして感じるか。
- クリア後に、より少ない工事でもう一度試したくなるか。
- タイマーを無効にしてもゲーム性が成立するか。

## 11. 非機能要件

### 11.1 パフォーマンス

- iPhone 17 Proで通常時60fpsを目標。
- iPhone 11 ProとiPad Pro 2018で継続的な操作不能や大幅なフレーム落ちを発生させない。
- ドメイン計算は描画と分離し、1手分の水流処理を短時間で完了する。
- 1フレーム内で過剰なCanvas状態変更や一時オブジェクト生成を避ける。
- 15分連続プレイでメモリが増加し続けない。
- バックグラウンド復帰後に固定ステップを無制限に追いつかせない。
- 初期転送量は軽量に保ち、不要な画像・フォント・ライブラリを含めない。

### 11.2 信頼性

- ゲームロジックで未処理例外を発生させない。
- 保存失敗で進行不能にしない。
- Canvas再生成後も入力リスナーを二重登録しない。
- Page Visibility復帰後にタイマー、音、水流を二重実行しない。
- 端末回転でゲーム状態を失わない。
- 確定ボタンの連打で施工を二重実行しない。
- プレビューと次の1水流ステップの実結果を一致させる。

### 11.3 セキュリティ・プライバシー

- MVPでは個人情報を収集しない。
- 外部APIへプレイデータを送信しない。
- 外部分析SDKを導入しない。
- localStorage以外へユーザーデータを保存しない。
- 将来オンライン機能を追加する場合は別計画と脅威分析を必須とする。

## 13. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| 水流が理解できない | 理不尽に感じる | 次の1ステップ予測、主流路、危険理由、失敗再生を表示 |
| 情報が多すぎる | 主要目的が分からない | 主要目的1つ、副目的最大1つ、主要HUD最大3指標 |
| 毎手の選択が弱い | 作業的になる | 2候補制、未使用候補持ち越し、固定候補列 |
| ランダムで勝敗が変わる | パズルとして不公平 | キャンペーンは固定雨列・固定候補列 |
| 自動確定で誤操作する | タッチ操作が理不尽 | 時間切れは見送り、確定ボタン必須 |
| タイマーが思考を妨げる | 初心者・アクセシビリティに不利 | 序盤は無制限、段階導入、延長・無制限設定 |
| 未来予測が強すぎる | 総当たり作業になる | 次の1水流ステップだけ表示 |
| 単純な堤防作りだけになる | 戦略性低下 | 排水能力、工事効率、一時貯水、複数目的を段階導入 |
| 水流演出が待ち時間になる | テンポ低下 | 非操作1.5秒以内、高速再生、重要イベントは省略しない |
| アイソメトリックでセルを誤選択する | 操作ストレス | 上面優先判定、指位置オフセット、仮置き保持、明示確定 |
| 縦向きで盤面が小さすぎる | iPhoneで遊びにくい | ボトムシート化し、盤面を単純縮小しない |
| テーマが乾いて見える | 面白さ・愛着不足 | ミニチュア模型表現、街の反応、安全排水の見せ場 |
| コアループ未検証でステージを量産する | 手戻り増大 | M4ゲーム性検証ゲートを通るまでステージ4～6を作らない |
| 元作品との類似性 | 公開リスク | 独自名称、独自UI、2候補制、ステージ制、予報・排水中心へ差別化 |
| 無ライセンスOSS混入 | 法務リスク | コード再利用禁止、依存監査、NOTICE管理 |
| タスク細分化 | 管理負荷 | マイルストーン単位でPRを構成し、遊べる縦切りを優先 |

## 15. 完成条件

### 15.1 ゲームロジック

- 同一ステージデータと同一操作列で常に同一結果になる。
- 水量が負にならない。
- 地形高さが仕様範囲外にならない。
- 地形上昇で水が消えない。
- 初期水量と追加雨量の合計が、盤面残量、安全排水、漏水の合計と一致する。浸水量は水を消さない被害値として別に検査する。
- セル走査順を変えても結果が変わらない。
- 安全排水と漏水が別集計される。
- 排水口処理能力が仕様どおり機能する。
- Undo後の盤面、候補、雨、評価、勝敗などの可逆ゲーム状態が操作前と一致する。revision、action ID、Undo使用記録、操作ログは巻き戻さない。
- Undo後に同じ操作をすると同じ結果になる。
- タイムアウト結果が施工見送りとして再現できる。
- 施工候補A／Bと持ち越しが操作ログで再現できる。

### 15.2 ゲーム性

- 毎手、2候補のどちらを選ぶかに意味がある。
- 6ステージを最後までプレイできる。
- 1ステージ3～5分程度で完了する。
- 各ステージの主要目的が1つに絞られている。
- 雨予報を読む行動が結果へ影響する。
- 安全排水と一時貯水の両方に役割がある。
- 水を止めるだけでなく、安全に流す判断が必要である。
- ステージ3以降に複数の有効解がある。
- ステージ6に最低2つの高評価方針がある。
- 単純な支配戦略で複数ステージを高評価突破できない。
- 水流を待ち時間ではなく答え合わせとして認識できる。
- クリア後に工事効率を改善する再挑戦理由がある。

### 15.3 分かりやすさ

- 初見プレイヤーが30秒以内に主要目的を説明できる。
- 次の2つの雨を確認できる。
- 配置前に変更セルと高さを確認できる。
- 次の1水流ステップを確認できる。
- 回転後の形状を確認できる。
- 漏水箇所と主原因を追跡できる。
- 危険度を色以外でも判断できる。
- 結果画面で改善点を1つ理解できる。
- プレイ中の主要指標が3つを超えない。

### 15.4 操作性

- 主要タップ対象が44 CSS px以上。
- 指を離しただけで施工されない。
- 同セル再タップで誤確定しない。
- ドラッグ中も仮置きが指に隠れない。
- 無効位置で手番やUndoを消費しない。
- 横スクロールがない。
- safe-areaでUIが隠れない。
- 盤面がUIまたは画面外に見切れない。
- 横向きと縦向きの両方でプレイ可能。
- 一時停止、再開、Undo、施工見送り、再挑戦が正常に動く。
- 連打で施工が二重確定しない。

### 15.5 パフォーマンス・品質保証

- iPhone 17 Proで通常時60fpsを目標とする。
- iPhone 11 ProとiPad Pro 2018で継続的な操作不能がない。
- 水流などの非操作時間が原則1.5秒以内。
- 15分連続プレイでメモリが増え続けない。
- TypeScript型検査成功。
- 単体テスト成功。
- 統合テスト成功。
- Playwright主要フロー成功。
- 本番ビルド成功。
- GitHub Pages環境で404やベースパス不具合がない。
- コンソールエラーがない。
- 未処理Promiseエラーがない。
- Critical／Highの既知不具合が0件。
- OSSライセンス一覧が確認済み。
- 独自名称・独自アセットが確認済み。

### 15.6 公開

- M4ゲーム性検証ゲートを通過している。
- 公開前独立レビューが完了している。
- iPhone 17 Pro、iPhone 11 Pro、iPad Pro 2018の実機確認が完了している。
