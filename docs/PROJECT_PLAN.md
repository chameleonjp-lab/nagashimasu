## 1. エグゼクティブサマリー

「ナガシマス」は、8×8の土地を組み替え、予告された降雨を受け止め、居住区を守りながら安全な排水先へ水を導く、タッチ操作中心の治水パズルゲームである。

AQUAQUA／Wetrix系作品の核である「地形を作る → 雨を受ける → 水の流れを観察する → 漏水箇所を修理する」という循環を参考にする。ただし、名称、ロゴ、画像、音声、キャラクター、ステージ、ソースコード、固有の画面構成は利用せず、独自の世界観、ルール、UI、アート、実装で構築する。

初期版は、フル3Dや本格的な流体力学を採用しない。整数ベースの決定論的なグリッド水流シミュレーションと、Canvas 2Dによるアイソメトリック疑似3D表示を組み合わせる。これにより、iPhoneでの安定性、操作の分かりやすさ、再現可能なテスト、短い開発サイクルを優先する。

### 採用方針

| 項目 | 決定 |

| 作品名 | ナガシマス |
| 世界観 | 独自の治水・防災テーマ |

| 外部ゲームエンジン | MVPでは使用しない |

## 2. 作品ビジョン

### 2.1 一文で表すゲーム

**次の雨を読み、限られた地形操作で水を受け止め、守る場所と流す場所を設計する治水パズル。**

### 2.2 プレイヤー体験の柱

1. **予測できること**  
   次の雨の位置、強さ、発生までの猶予を事前に見せる。失敗をランダム事故ではなく、読み違いまたは設計不足として理解できるようにする。

2. **置いた結果を理解できること**  
   パーツを確定する前に、変化するセル、高さ、予想流路、危険度の増減を表示する。

3. **水を止めるだけでなく流すこと**  
   水を全量ため込むのではなく、貯水池、排水口、安全水路へ制御して流す。作品名「ナガシマス」の意味をゲームの中心に置く。

4. **短時間でも戦略が残ること**  
   1ステージ3～5分程度とし、操作速度だけでなく、地形の順序、雨予報、排水能力、将来の修理余地が結果を左右する。

5. **タッチ操作の失敗を理不尽にしないこと**  
   大きな操作対象、明確な確定操作、無効配置の非消費、ステージ中1回の完全Undoを用意する。

### 2.3 独自化の中心

- エンドレスに耐えるだけでなく、目的の異なる短い治水ステージを攻略する。
- 雨を完全ランダムにせず、2イベント先まで予報する。
- 居住区保護、貯水、排水、被害抑制を同時に評価する。
- 水量と地形高だけでなく、「危険な流向」を表示する。
- セミリアルタイム化し、スマートフォンで考える猶予と緊張感を両立する。
- 地形操作量が少ないほど高評価になる「工事効率」を導入する。

### 2.4 MVPで目指さないこと

- 元作品の完全再現
- 元作品のパーツ形状、演出、画面構成の模倣
- 高精度な流体力学シミュレーター
- フル3Dカメラ操作
- 大規模なオンラインサービス
- 長期運営を前提としたランキングやアカウント管理

## 3. コアルール

### 3.1 盤面

- 基本盤面は8×8の64セル。
- 各セルは最低限、次の状態を持つ。
  - 地形高さ
  - 水量
  - セル種別
  - 排水口フラグ
  - 保護対象フラグ
  - 漏水可能フラグ
  - 危険度
- 地形高さの初期範囲は0～6段を基準とする。
- 水量は整数単位で扱う。
- 斜面や水面の滑らかな見た目は描画側で補間し、ルール判定には使わない。

### 3.2 セル種別

MVPでは次を使用する。

- 通常地面
- 保護対象地面
- 貯水対象地面
- 排水口
- 盤外流出辺

災害で壊れる地面、橋、ポンプ、門、水門などはMVP後の拡張対象とする。

### 3.3 地形パーツ

MVPのパーツはデータ駆動で定義し、形状や効果量をコードへ直書きしない。

- **上昇パーツ:** 地形を1段上げる。初期3形状。
- **下降パーツ:** 地形を1段下げる。初期2形状。
- **回転:** 90度単位。
- **配置制約:** 盤外、上限超過、下限超過、変更禁止セルへの配置は無効。
- **無効配置:** 手番、タイマー、Undo権を消費しない。

初期形状数はプレイテスト用の基準であり、面白さと視認性を検証して増減する。

### 3.4 セミリアルタイム進行

1手は次のフェーズで進む。

1. **予報フェーズ**  
   次の雨の位置、強さ、発生までの手数を表示する。

2. **計画フェーズ**  
   プレイヤーは現在パーツの位置と向きを決める。初期制限時間は12秒、調整範囲は8～16秒とする。

3. **確認フェーズ**  
   変更セル、変更後の高さ、予想される主流路、危険度変化を半透明で表示する。

4. **確定フェーズ**  
   配置を確定する。時間切れ時は、その時点の有効なプレビューを確定する。有効な配置がない場合はパス扱いとする。

5. **降雨フェーズ**  
   発生条件を満たした雨イベントを適用する。

6. **水流フェーズ**  
   水流シミュレーションを複数固定ステップ進め、アニメーションで変化を示す。初期値は1手あたり4ステップ、調整範囲は2～6ステップとする。

7. **評価フェーズ**  
   漏水、排水、浸水、保護対象、スコア、クリア・失敗条件を評価する。

時間制限は緊張感のために使用するが、水流計算結果を実時間やフレームレートへ依存させない。

### 3.5 雨予報

- 常に次の2つの雨イベントを表示する。
- 表示内容は、範囲、強度、発生までの手数。
- 雨範囲は盤面上の模様、輪郭、アニメーションで表示する。
- 色だけで雨の強弱を区別しない。
- シード付き疑似乱数で雨イベントを生成し、同じシードと操作列から同じ結果を得られるようにする。
- ステージごとに雨イベントを固定定義する方式と、シード生成方式の両方を許容する。

### 3.6 水流

MVPでは上下左右の4近傍のみを使用する。

各セルの水面レベルを次で定義する。

`水面レベル = 地形高さ × 高さ係数 + 水量`

1回の固定ステップでは次を行う。

1. 現在セルと上下左右の水面レベルを比較する。
2. 現在セルより低い隣接先を抽出する。
3. 移動可能量を、現在水量、勾配、1ステップ上限から決定する。
4. 移動量を差分バッファへ記録する。
5. 全セルの計算後に差分を一括反映する。
6. 排水口へ入った水と盤外へ漏れた水を別々に集計する。

計算中に隣接セルを直接更新しない。これにより、セルを走査する順番で結果が変わる問題を防ぐ。

複数の隣接先が同じ最低水面の場合は均等分配し、整数除算の余りはセル番号と水流ステップから決定する循環順で配る。常に同じ方向を優先する偏りを抑えながら、結果の再現性を維持する。

MVPでは蒸発、浸透、波、飛沫の物理判定を扱わない。必要な見た目は表示演出として実装する。

### 3.7 排水と漏水

- **排水:** 指定された排水口へ安全に流れた水。原則としてプラス評価。
- **漏水:** 盤外の非安全辺へ流出した水。失敗ゲージとマイナス評価へ加算。
- **浸水:** 保護対象セルの許容量を超えた水。重大なマイナス評価。
- **貯水:** 指定された貯水セルに残った水。ステージ目的に応じて評価。

排水口には1ステップあたりの処理能力を設定できる。排水口へ水を集めすぎると逆流または滞留するため、単に低い道を作るだけでは最適解にならない構造を作る。

### 3.8 危険度表示

危険度はプレイヤーが次の一手を判断するための説明用指標であり、内部物理を隠すための曖昧な数値にはしない。

最低限、次を反映する。

- 盤外または保護対象へ向かう水の勾配
- 現在水量
- 周囲の堤防余裕
- 次回雨量
- 排水口までの経路
- 排水能力の超過見込み

表示段階は「安全」「注意」「危険」「決壊寸前」の4段階を基準とし、色、輪郭、模様、矢印、短い説明を併用する。

### 3.9 Undo

- 1ステージにつき1回だけ使用できる。
- 直前の有効な配置1手を完全に取り消す。
- 次の配置を確定する前まで使用できる。
- 地形だけでなく、次をすべて復元する。
  - 地形
  - 水量
  - 排水量
  - 漏水量
  - 浸水量
  - スコア
  - 手数
  - 現在パーツと次パーツ
  - 雨イベントキュー
  - 乱数状態
  - 勝敗状態
- 無効操作や単なる選択変更には消費しない。

### 3.10 ステージクリア型MVP

MVPは6ステージを基準とする。

| ステージ | 主な学習・目的 |
|---|---|
| 1 | 上昇パーツで堤防を作り、指定量を貯水する |
| 2 | 下降パーツで水路を作り、排水口へ導く |
| 3 | 雨予報を読み、保護対象の浸水を防ぐ |
| 4 | 排水口の能力上限を理解し、複数経路へ分散する |
| 5 | 強雨と連続雨に対し、貯水と排水を両立する |
| 6 | 上昇・下降・予報・排水・保護を統合した最終ステージ |

各ステージは3～5分程度を目標とする。チュートリアル説明はプレイを止める長文ではなく、必要なタイミングで盤面上に短く表示する。

### 3.11 スコアと評価

ステージクリアの成否とスコアを分離する。

**クリア条件の例**

- 規定手数または規定雨イベントを完了する。
- 保護対象の被害が許容値以下である。
- 漏水ゲージが上限未満である。
- 必須排水量または必須貯水量を満たす。

**スコア構成**

- 安全排水量
- 有効貯水量
- 保護対象の残存率
- 漏水の少なさ
- 浸水被害の少なさ
- 使用した地形操作量の少なさ
- 未使用Undoボーナス
- 残り時間は小さな補助点に留め、操作速度が支配的にならないようにする

評価はS／A／B／Cの4段階を基準とする。初回クリアは低評価でも進行可能とし、最適化を再挑戦の動機にする。

### 3.12 失敗条件

- 漏水ゲージが上限に達する。
- 必須保護対象が規定量以上浸水する。
- ステージ固有の必須条件を達成不能な状態になる。

失敗時は、最初に破綻した箇所、最大の漏水経路、排水能力超過、予報された雨への準備不足を簡潔に示す。

## 4. UI・UX計画

### 4.1 正規レイアウト

横向きを正規レイアウトとする。

- **中央:** 8×8アイソメトリック盤面
- **左:** ステージ目的、雨予報、残り手数
- **右:** 現在パーツ、次パーツ、回転、確定、Undo
- **上部:** スコア、漏水、排水、保護状態
- **下部:** 状況説明、危険理由、短いチュートリアル

縦向きではプレイ開始前に横向きを推奨する。強制回転や操作不能にはせず、縮小レイアウトで最低限プレイ可能にする。

### 4.2 タッチ操作

- Pointer Eventsでタッチとマウスを共通化する。
- タップでセル選択、ボタンで回転、明示的な確定ボタンで配置する。
- ドラッグは補助操作とし、必須にしない。
- 主要タップ領域は44 CSS px以上。
- 選択セルと実際の適用セルを常に一致させる。
- 盤面の端で指やUIに隠れないよう余白を確保する。
- ページスクロール、ダブルタップ拡大、長押しメニューがゲーム操作を妨害しないよう制御する。
- 横スクロールを発生させない。

### 4.3 配置プレビュー

配置前に次を表示する。

- 対象セルの輪郭
- 上昇／下降後の高さ
- 配置可能／不可能
- 予想主流路
- 危険度の増減
- 排水口到達見込み

プレビューは参考情報であり、完全な未来予測を表示する必要はない。ただし、表示した結果と確定後の最初の水流が矛盾しないようにする。

### 4.4 水の視認性

- 水量に応じて水面の高さを変える。
- 流れた方向へ短い帯または粒子を表示する。
- 漏水箇所には盤外へ向かう矢印と波紋を表示する。
- 排水は漏水と異なる形状・音で示す。
- 地形、水、水予報、危険表示が同系色で混同しない配色にする。
- 色覚に依存せず、模様とアイコンを併用する。

### 4.5 音

MVPのロジック完成までは音を必須にしない。追加時は次を守る。

- 初期設定は無音。
- ユーザー操作で有効化できる。
- 配置、雨、正常排水、漏水、浸水、クリア、失敗で役割を分ける。
- 音がなくても全情報を理解できる。

## 5. 技術選定

### 5.1 採用技術

| 領域 | 技術 | 採用理由 |
|---|---|---|
| 言語 | TypeScript | 状態構造とルールの型安全性、リファクタリング、テスト容易性 |
| ビルド | Vite | 小規模構成、ES Modules、開発サーバー、本番ビルド |
| 描画 | Canvas 2D | 64セルでは十分。iOS Safariの安定性と軽量性を優先 |
| HUD | HTML／CSS | 文字、ボタン、アクセシビリティ、safe-area対応 |
| 水流 | 独自整数グリッド方式 | 決定論、再現性、テスト容易性、低負荷 |
| 状態配列 | TypedArray | 固定盤面、予測可能なメモリ、スナップショット容易性 |
| 単体テスト | Vitest | TypeScript／Viteとの統合 |
| E2E | Playwright | ChromiumとWebKitで主要フローを検証 |
| 保存 | localStorage | MVPにサーバー不要 |
| 配信 | GitHub Pages | 静的配信で無料運用可能 |

### 5.2 MVPで採用しない技術

- Phaser
- PixiJS
- Three.js
- WebGLによるGPU流体演算
- WebGPU
- 物理エンジン
- Supabase
- サーバーレス関数
- ログイン
- オンラインランキング

描画表現がCanvas 2Dの限界に達した場合でも、ゲームロジックを描画から分離し、表示層だけをPixiJSまたはThree.jsへ交換できる構成にする。

## 6. システム構成

### 6.1 レイヤー

#### Domain

ゲームの正解を決める。DOM、Canvas、音、localStorage、実時間へ依存しない。

- 盤面状態
- 水流
- 地形操作
- 雨イベント
- 排水・漏水・浸水
- スコア
- クリア・失敗判定
- Undoスナップショット
- シード付き乱数

#### Application

ゲーム進行を調停する。

- ステージ開始・終了
- フェーズ遷移
- タイマー入力のコマンド化
- 現在／次パーツ
- 操作ログ
- 一時停止
- チュートリアル進行

#### Presentation

状態を表示し、入力をコマンドへ変換する。

- アイソメトリック盤面
- HUD
- プレビュー
- 水流アニメーション
- 雨演出
- 結果画面
- タッチ入力

#### Platform

ブラウザ機能を隔離する。

- localStorage
- Page Visibility API
- resize／orientationchange
- safe-area
- 音設定
- GitHub Pagesのベースパス

### 6.2 計画ディレクトリ

```text
/
├─ index.html
├─ src/
│  ├─ domain/
│  ├─ application/
│  ├─ presentation/
│  ├─ platform/
│  └─ main.ts
├─ data/
│  ├─ stages/
│  ├─ pieces/
│  └─ balance/
├─ tests/
│  ├─ unit/
│  ├─ integration/
│  └─ e2e/
├─ docs/
└─ public/
```

これは実装時の初期案であり、単一HTMLへ統合することを前提としない。

### 6.3 主要状態

固定64セルのため、次の配列構成を基準とする。

- `height`: `Int8Array`
- `water`: `Uint16Array`
- `waterDelta`: `Int32Array`
- `cellFlags`: `Uint8Array`
- `danger`: `Uint8Array`

ゲーム全体では次を保持する。

- ステージID
- シード
- 乱数状態
- 現在手数
- フェーズ
- 制限時間状態
- 現在パーツ／次パーツ
- 雨イベントキュー
- 排水量
- 漏水量
- 浸水量
- スコア
- Undo使用状態
- 操作ログ

### 6.4 決定論

同じステージ、シード、操作列から同じ結果を得ることを必須とする。

- ゲーム判定に`Math.random()`を直接使用しない。
- 水流を描画フレーム時間へ依存させない。
- 浮動小数点値を勝敗判定へ使用しない。
- タイマー切れは「タイムアウトコマンド」として操作ログへ記録する。
- 操作ログからゲーム全体を再生できる構造にする。

### 6.5 Undo実装

MVPの盤面は小さいため、複雑な差分圧縮より安全性を優先し、直前手の完全スナップショットを保持する。

- TypedArrayを複製
- スカラー状態をコピー
- 雨キューをコピー
- 乱数状態をコピー
- 現在／次パーツをコピー

64セル規模ではメモリ負荷は無視でき、復元漏れのリスクを下げられる。

### 6.6 保存

localStorageには次だけを保存する。

- 設定
- クリア済みステージ
- 最高評価
- チュートリアル既読状態
- 必要に応じて中断中ステージ

保存データへスキーマバージョンを付ける。破損時はゲーム全体を停止させず、安全に初期化できるようにする。

## 7. OSS調査結果

- [GithubPrankster/wetrix](https://github.com/GithubPrankster/wetrix)はN64版Wetrixの逆コンパイル研究であり、正規入手ROMを要求し、ライセンスも設定されていない。コード、データ、アセットを本作へ持ち込まない。
- [evanw/webgl-water](https://github.com/evanw/webgl-water)は著名な水面デモだが、リポジトリに明示ライセンスがないため再利用対象にしない。
- ライセンス未設定リポジトリは、公開されていても再利用可能とは判断しない。

### 7.3 OSS採用結論

MVPではゲーム本体へ外部ゲームエンジンや水シミュレーションOSSを組み込まない。

採用するのは次の設計思想のみである。

- 純粋ロジックと描画の分離
- TypedArrayによる盤面状態
- 固定ステップ
- 読み書き差分バッファ
- シード付き乱数
- 操作ログによる再現
- 完全スナップショットUndo
- 機能検出と安全なフォールバック
- 高さ場で表現できないものを仕様上明示する姿勢

実装時にOSSコードを引用または移植する場合は、別途ライセンス確認、採用理由、変更箇所、著作権表示を記録し、ユーザー承認を得る。

## 11. 非機能要件

### 11.1 パフォーマンス

- iPhone 17 Proで通常時60fpsを目標。
- iPhone 11 ProとiPad Pro 2018で継続的な操作不能や大幅なフレーム落ちを発生させない。
- ドメイン計算は描画と分離し、1手分の水流処理を短時間で完了する。
- 1フレーム内で過剰なCanvas状態変更や一時オブジェクト生成を避ける。
- 15分連続プレイでメモリが増加し続けない。
- バックグラウンド復帰後に固定ステップを無制限に追いつかせない。
- 初期転送量は軽量に保ち、不要な画像・フォント・ライブラリを含めない。

### 11.2 アクセシビリティ

- 色だけに依存しない。
- 主要ボタンにテキストまたは明確なラベルを付ける。
- `aria-label`を適切に設定する。
- 文字サイズを極端に小さくしない。
- 点滅は抑制し、強い点滅を使用しない。
- 音なしでプレイ可能。
- アニメーション削減設定を尊重する。

### 11.3 信頼性

- ゲームロジックで未処理例外を発生させない。
- 保存失敗で進行不能にしない。
- Canvas再生成後も入力リスナーを二重登録しない。
- Page Visibility復帰後にタイマー、音、水流を二重実行しない。
- 端末回転でゲーム状態を失わない。

### 11.4 セキュリティ・プライバシー

- MVPでは個人情報を収集しない。
- 外部APIへプレイデータを送信しない。
- 外部分析SDKを導入しない。
- localStorage以外へユーザーデータを保存しない。
- 将来オンライン機能を追加する場合は別計画と脅威分析を必須とする。

## 13. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| 水流が理解できない | 理不尽に感じる | 主流路、危険理由、雨予報、配置プレビューを表示 |
| 単純な堤防作りだけになる | 戦略性低下 | 排水能力、保護対象、工事効率、複数目的を導入 |
| タイマーが思考を妨げる | タッチ操作で不利 | 初期12秒、チュートリアル中停止、調整可能な設計 |
| 水計算を高度化しすぎる | 開発遅延・不具合 | 整数4近傍方式を固定し、物理表現は演出へ分離 |
| 盤面が小さく単調 | リプレイ性不足 | 初期地形、雨順、排水位置、保護対象、評価条件を変える |
| Canvasがぼやける | 視認性低下 | devicePixelRatio対応とresize再構築 |
| iOS復帰で時間が飛ぶ | 即失敗 | 非表示中は完全停止し、復帰時に時計を再基準化 |
| 元作品との類似性 | 公開リスク | 独自名称、独自UI、ステージ制、予報・排水中心へ差別化 |
| 無ライセンスOSS混入 | 法務リスク | コード再利用禁止、依存監査、NOTICE管理 |
| タスク細分化 | 管理負荷 | マイルストーン単位でPRを構成し、細分化しすぎない |
