# PR6：表示用再計算の抑制

基点はPR5 #62マージ後のmain `5cddcbdadbbd29dfdf44417a1c0af1fe52275c2b`。Draft PRの対象SHAはPR本文にも記録する。

## 目的

タイマー更新や水流再生のフレーム更新は表示だけを進めるため、同じ盤面・同じ仮置きから作る合法セル一覧と予測を毎回計算し直さない。表示更新を軽くしつつ、受理済み操作とDomainの決定論的な結果はそのまま保つ。

## 実装

- `StageController.view` を、`revision`・`nextActionId`・選択候補・仮置きスロット／座標／回転のキーでキャッシュする。
- 合法セル一覧は、盤面のrevision・候補・回転が同じ間は再利用する。仮置き座標の変更や候補切替では、表示用のviewと関連予測を明示的に破棄する。
- 仮置きの検証結果と施工プレビューを同じキーで再利用する。
- `previewSkip`／`previewTimeout` は、操作種別・revision・actionIdが同じ間は再利用する。
- タイマーのtickはタイマー表示だけを更新し、盤面・候補・予測の通常renderを呼び出さない。
- セッションの受理、候補選択、仮置き、回転、取消でキャッシュを破棄する。キャッシュは表示用の証拠だけを保持し、`StageSession`の状態を書き換えない。

水流計算、勝敗、スコア、候補補給、Replay、Undo、保存形式、ランキング送信、既存の再生表示は変更していない。

## 自動検査

- 同じ状態で `StageController.view`、合法セル、検証、施工プレビュー、見送り予測が同一の導出結果を再利用することを検査する。
- 候補切替、仮置き、回転、受理後にキャッシュが破棄され、最新の表示結果へ更新されることを検査する。
- 既存の `npm run check`（型検査、46ファイルの単体テスト、Domain build/smoke、画面build/smoke）を合格させる。

## 計測の扱い

監査時の基準は、ステージ3の仮置き中にviewを100回取得した場合の `validate 6500回`、`preview 100回`、ローカル267.6msだった。今回の自動検査はキャッシュ再利用と無効化を保証するが、DOM・GPU・iPhoneのframe timeや入力応答を測るものではない。実機確認では、同一仮置きでタイマーが動いている間に入力遅延や発熱が増えないことを別途確認する。

## iPhone 17 Pro確認手順

1. 所有者限定の確認ページでステージ3を開始し、候補を選んで盤面へ仮置きする。
2. 仮置きを保持したままタイマーを動かし、候補の合法セル、施工プレビュー、危険理由が崩れず、盤面タップの反応が遅くならないことを確認する。
3. 回転、候補切替、仮置き取消、別セルの仮置きで表示が最新になることを確認する。
4. 見送り、施工確定、Undo、再挑戦で結果・水流・スコア・保存が従来どおりであることを確認する。
5. WebGL有効時のframe time、発熱、復帰、縦横画面、文字拡大、VoiceOver、初見プレイ3名、Sol・Highの独立レビューは別のM4ゲートとして扱い、自動検査だけで完了にしない。

iPhone 17 Pro Safari実機、WebGL有効時のframe time・タップ精度・発熱・復帰、縦横画面、文字拡大、VoiceOver、初見プレイ3名、Sol・Highの独立レビューは未確認である。
