# ADR 0016: 手番の因果を視覚化する

- **状態:** Accepted／M4実機再検証待ち
- **日付:** 2026-08-29（JST）

## 背景

PR #33でゲーム目的、操作手順、手番結果を文章化したが、iPhone実機ではプレイヤーが「何をするゲームか」「何をすればよいか」「何が起きたか」を理解できないまま終了した。文章だけでは、元作品が持つ地形の高さ、水の滞留、雨、水流、流出の因果を盤面上で追えない。

## 決定

- 施工前後の地形差を、立体的な側面、施工セルの発光、上下矢印、施工前の点線輪郭で表示する。
- 地形の側面へ高さ単位の継ぎ目を描き、平面の色違いだけに依存しない。
- 水量が0より大きいセルは、量に応じた水面、水塊の側面、波紋、数値で表示する。プレビューでは`boardAfterNextFlow`の水量を使い、確定前の予測と盤面を一致させる。
- 雨は対象セル上空の雲、雨筋、着水波紋、雨量で表示する。予報にも雲を表示し、発生中の雨はtraceの`rain`区間で落下させる。
- 水流は既存の`WaterTransfer`を再計算せず、流路、移動粒子、移動量、移動先の波紋として表示する。安全排水は緑、危険流出は赤で区別する。
- 手番上部に「工事 → 雨 → 水流 → 結果」の視覚タイムラインを置き、盤面上にも現在phase、目標進捗、終端結果を表示する。
- クリア／失敗の表示は、StageSessionの終端phaseとfailureReasonsから作り、表示側で原因を推測しない。
- これらはPresentation側の変更に限定し、StageSessionの水流計算、クリア判定、スコア、保存、操作ログは変更しない。

## 却下した案

- 工事・雨・水流を説明文だけで表す案は、実機で因果が伝わらなかったため採用しない。
- 表示側で水流を再計算して中間盤面を生成する案は、Domainの結果と表示がずれるため採用しない。
- 元作品の画像、音声、ロゴ、固有アセットを流用する案は採用しない。独自のCanvas描画で表現する。

Canvasで実現していた視覚要件をThree.jsへ引き継ぐ。

## 検証

- `waterVisualLevel`が水量を bounded な表示レベルへ決定論的に変換することを検査する。
- `flowParticlePositions`が既存の転送元・転送先から決定論的な複数粒子を生成することを検査する。
- app smokeで目標メーター、手番タイムライン、雲・水面・粒子・結果表示の本番バンドルを検査する。
- `npm run check`通過後、公開版を更新し、iPhone実機で「目的理解」「最初の工事」「雨と水流の視認」「結果原因の説明」を再測定する。M4完了、独立レビュー、M5着手とはまだ扱わない。
