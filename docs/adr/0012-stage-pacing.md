# ADR 0012: M4ステージ手数・雨間隔調整

## 状態

Accepted／M4ゲーム性検証中

## 背景

M4の画面導線を通して確認したところ、ステージ1〜3は最短の有効解がステージ1・2で1施工、ステージ3で2施工なのに対し、最大手数が8／9／10だった。解決後に同じ候補を使わず見送る手が長く続くと、雨予報を読んで候補を選ぶ判断が薄くなり、短時間パズルのテンポも崩れる。

## 決定

- 画面なしの完走条件と水流アルゴリズムを維持したまま、組み込みステージの手数をステージ1＝3、ステージ2＝3、ステージ3＝4へ変更する。
- ステージ1と2の雨は2・3手目、ステージ3の雨は2・3・4手目に置く。候補列も各最大手数に合わせ、最後まで受理できる長さを保つ。
- ステージ2の安全排水目標と評価の流量制御基準を16から8へ変更する。短い2回の雨列で安全に排水できる量が8であり、16のままでは手数を短くした結果だけで失敗するためである。
- ステージ定義の`dataVersion`を`1_1_0`へ上げ、3ステージの`definitionDigest`を更新する。旧版の保存は定義不一致として再開せず、新しいステージを開始する。
- これはステージデータのテンポ調整であり、M1の水流規則、M2の手番原子性、評価計算、保存・再生の形式は変更しない。

## 保持するもの

- ステージ1の貯水、ステージ2の安全排水、ステージ3の上下併用という学習順を保つ。
- ステージ3は上げる施工だけ、下げる施工だけでは解けず、上下を組み合わせる必要がある構造を保つ。
- 各ステージの固定雨・固定候補、複数解、支配戦略検査を画面なしテストで確認する。
- この変更だけでM4ゲーム性検証を完了とはしない。実際の画面で、2候補の選択が毎手意味を持つか、3〜5分の緊張曲線になるかを手動確認する。

## 検証

- ステージ1〜3の最大手数、雨手数、候補列長、ステージ2目標を固定値テストで確認する。
- 既存のステージ完走、複数解、支配戦略、予報表示、StageSaveのテストを通す。
- 型検査、全単体テスト、ドメイン／画面build・smoke、`git diff --check`を通す。
