# ADR 0002: M2ステージ進行と高レベル操作

- 状態: 採用
- 決定日: 2026-08-13
- ステージルール版: `nagashimasu-stage-rules-v1`
- ステージ再生記録版: `nagashimasu-stage-replay-v1`
- 依存する水流ルール版: `nagashimasu-water-v1`

## 目的

M2で施工候補、雨予報、手番進行、評価、タイムアウト、Undoを追加しても、次を維持する。

- 同じステージ定義、セッション設定、受理済み操作列から同じ結果を得る。
- 施工から評価までの1手を、部分的な状態を残さず一括して確定する。
- 連打、タイマー競合、再送によって同じ手が二重に進まない。
- 壊れたステージデータ、再生記録、保存値を、実行前または上限内で拒否する。
- M1の水流ルール、公開型、再生記録との互換性を壊さない。

本ADRはM2のドメイン契約の正本とする。画面のアニメーション時間、壁時計、Canvas、DOM、保存媒体はこの契約に含めない。

## 版と正本

M2では次の版を独立して管理する。

| 対象 | 版 | 正本 |
|---|---|---|
| 水流計算 | `nagashimasu-water-v1` | ADR 0001とM1ドメイン |
| ステージ進行 | `nagashimasu-stage-rules-v1` | 本ADRとM2ドメイン |
| ステージ再生 | `nagashimasu-stage-replay-v1` | 受理済み高レベル操作列 |

M1の`SimulationCommand`、`OperationLogEntry`、`ReplayLogV1`へM2の操作を追加しない。M1の低レベル操作記録は水流の検査またはデバッグには使用できるが、ゲーム全体を再生する正本にはしない。

次のいずれかを変更するときは、該当する版を更新する。

- 候補の補充、雨の発生、手番、勝敗、Undo、評価の意味
- 受理される高レベル操作または状態ハッシュの対象
- 同じステージ定義と操作から得られる盤面または評価
- 再生記録の必須フィールド、検証順、上限

## StageDefinitionの検証

### 未検証値を直接実行しない

JSON、テストfixture、保存値などの入力は`unknown`として受け取り、strictな実行時validatorを通す。TypeScriptの型注釈だけを信頼しない。

validatorは入力を新しいプレーンな値へコピーして正規化し、未知のキー、関数、アクセサ、欠損、余分な配列要素を拒否する。検証済み定義は深く凍結し、未検証の元オブジェクトへの参照を保持しない。

最低限、次を検証する。

- スキーマ版、ステージID、ステージデータ版
- M1の`BoardDefinition`として有効な64セルの初期盤面
- 最大手数は1～64
- 1手の水流は2～6固定ステップ
- パーツID、効果量、回転中心、1～3個の重複しない相対セル
- パーツカタログは1～32件で、参照するIDがすべて存在すること
- 施工候補列は初期2枠と最大手数分の補充を含むこと
- 雨イベントの手番、正規順、セル番号、雨量、参照先
- 主要目的は1つ、副目的は最大1つ、失敗条件は最大2つ
- 評価係数、上限、S／A／B／C閾値が安全な整数範囲にあること
- 文字列、配列、イベント数に明示的な上限があること

MVPの施工候補列は`最大手数 + 2`件とする。先頭2件を候補A／Bへ入れ、使用した側だけを次の要素で補充する。施工見送りとタイムアウトでは両候補を維持し、列位置を進めない。

雨イベントはステージ定義から導出し、プレイヤー操作のpayloadから雨量や対象セルを受け取らない。同一イベント内の重複セルを拒否し、同一手番のイベントは定義上の正規順で集約する。

M2のステージデータでは、初期盤面水量と全雨量の合計を65,535以下に制限する。この保守上限により、すべての水が1セルへ集中しても`Uint16`の上限を超えない。将来この上限を緩和する場合は、到達可能状態の別の安全証明とルール版更新を必要とする。

施工禁止セル、貯水対象など、水流計算に影響しない静的属性はStageDefinition側のmaskとして保持する。M1の`BoardSnapshot`や水流用`CellFlag`へ暗黙に追加しない。

### 定義digest

validatorは検証済み定義と、参照する検証済みパーツ定義を決定論的なキー順で直列化し、専用の64ビットFNV-1a検査値を作る。これを16文字の小文字16進数`definitionDigest`として扱う。

同じステージIDとデータ版でも内容が変わればdigestが変わる。再生時はIDやデータ版だけでなくdigestも一致させる。この値は偶発的な不一致や破損を検出する検査値であり、第三者による改ざんを証明する署名ではない。

## ステージ状態

権威あるステージ状態は、最低限次を保持する。

- ステージID、ステージデータ版、定義digest、ルール版
- M1の`BoardSnapshot`
- 完了手数と次に発生する雨の位置
- 候補A／Bと候補列の次位置
- 乱数状態
- 安全排水、危険流出、浸水、工事量、排水能力超過などの評価材料
- 権威あるフェーズと勝敗
- Undo使用状態と直前手のcheckpoint
- 単調増加するrevision、次のaction ID、直前に受理した操作のfingerprint

ステージ定義そのものと操作ログは状態へ再帰的に埋め込まない。定義はdigestで参照し、操作ログは状態ハッシュの外側で保持する。

## 権威あるフェーズ

ドメインが永続化する権威あるフェーズは次の3つに限定する。

- `awaiting-turn`: 次の施工確定、見送り、タイムアウトを受理できる。
- `cleared`: クリア済み。条件を満たす直前手のUndoだけを受理できる。
- `failed`: 失敗済み。条件を満たす直前手のUndoだけを受理できる。

施工、降雨、水流、評価は1回の原子的な計算の内部段階であり、途中状態を確定しない。計算結果は施工、雨、水流固定ステップ、評価の正規順traceを返す。

状況確認、候補選択、仮置き、確認、雨アニメーション、水流アニメーション、結果表示はApplication／Presentationの状態機械が扱う。表示側の`advancePhase`、再生速度、描画フレームによってドメイン計算を再実行しない。

表示用の配置検証と「次の1歩」previewは、本番と同じ配置解決・雨・水流関数を状態cloneへ適用する。元状態、候補、手数、評価、ログを変更せず、previewの最初の固定ステップは同じ操作を確定した結果の最初の固定ステップと一致させる。Presentationが独自の近似物理を実装してはならない。

## 高レベル操作と冪等性

受理対象の高レベル操作は次とする。

- 施工確定: 候補枠0または1、基準セル、0～3の四半回転
- 手動施工見送り
- タイムアウト
- 直前手のUndo

施工操作はパーツIDや雨イベントをpayloadへ複製しない。候補枠からパーツを、ステージ定義と現在手数から雨を決定する。これにより、操作記録がステージ状態と異なる内容を注入できないようにする。

すべての操作は、非負の安全な整数`actionId`と`expectedRevision`を持つ。

1. `expectedRevision`が現在値と一致し、`actionId`が次の値なら検証を続ける。
2. 直前に受理した操作と同じ`actionId`かつ同じ正規化payloadなら、再送として状態とログを変更せず同じ確定結果を返す。
3. 同じ`actionId`でpayloadが異なる場合はID衝突として拒否する。
4. 古いrevision、飛び越したID、以前のIDはstale操作として拒否する。
5. 無効配置、違法フェーズ、検証エラーは手数、候補、Undo、revision、action ID、ログを消費しない。

同じrevisionを見た施工確定とタイムアウトが競合した場合、直列化されて先に受理された1件だけが手を進める。後から到着した操作はstaleまたはID衝突として拒否する。

## 1手の原子性

施工確定、手動見送り、タイムアウトの1件を1手のトランザクション境界とする。

1. 操作、フェーズ、ID、revisionを検証する。
2. 現在の全ステージ状態から独立した作業用cloneを作る。
3. Undo用checkpointを作る。
4. 施工確定なら、全対象セルと高さを検証してから地形を変更する。
5. この手に発生する雨を正規順で適用する。
6. ステージ定義の固定ステップ数だけM1の水流を進める。
7. 全固定ステップの証拠を集約し、勝敗と評価を計算する。
8. 候補、雨位置、手数、評価材料、フェーズを更新する。
9. full state hashと高レベル操作記録を作る。
10. すべて成功した場合だけ、状態と操作記録を同時に確定する。

M1の`WaterSimulation.execute`を元のセッションへ施工、雨、水流の順で直接複数回呼び、途中状態を確定してはならない。M1のmutableな処理を利用する場合は、必ず作業用cloneまたは一時simulationの内側だけで実行する。

どの内部段階で例外または不変条件違反が起きても、元の盤面、水収支、候補、雨位置、評価、Undo、revision、action ID、ログは完全に不変とする。

## タイムアウト

壁時計、`Date.now()`、`performance.now()`、`setTimeout()`、Page VisibilityはApplication／Platformだけが扱う。ドメインは経過ミリ秒を判定しない。

タイマーが有効なセッションでApplicationが期限到達を確認した場合、現在の`actionId`と`expectedRevision`を持つタイムアウト操作を送る。タイムアウトは手動見送りと同じ盤面進行を行うが、再生記録では別の操作種別として残す。

- 仮置きは確定せず破棄する。
- 候補A／Bと候補列位置は維持する。
- 雨、水流、評価、手数は通常どおり進める。
- 無制限設定ではタイムアウト操作を拒否する。
- pause、Undo、次手への遷移でrevisionが変わった後の古いcallbackを拒否する。

タイマー設定はステージスコアへ加えない。ただし再生の前提を明確にするため、セッション設定としてStageReplayのheaderへ記録する。

## Undo

Undoは1ステージ1回とし、直前の有効な施工確定、手動見送り、タイムアウトだけを対象にする。次の有効な手を確定する前であれば、直前手で`cleared`または`failed`になった後も使用できる。

checkpointには、直前手の前に存在した可逆ゲーム状態だけを保持する。

- M1の盤面全配列と水量収支counter
- 完了手数、候補A／B、候補列位置、雨位置
- 乱数状態
- 浸水、排水能力超過、工事量を含む評価材料
- 勝敗と権威あるフェーズ

checkpointへ操作ログ、別のcheckpoint、revision、action IDを再帰的に含めない。

Undo成功時はcheckpointの可逆状態を復元したうえで、次を行う。

- `undoUsed`をtrueにする。
- checkpointを破棄する。
- revisionとaction IDを単調に進める。
- 既存ログを削除せず、Undo操作を新しいentryとして追記する。

したがって、Undo後のfull state hashは操作前のfull state hashと一致しない。検査には2種類のhashを使用する。

- `reversibleGameplayHash`: Undo対象の可逆ゲーム状態だけを含む。Undo後は直前手の操作前と一致する。
- `fullStateHash`: 可逆状態に加え、`undoUsed`、checkpoint、revision、次のaction ID、直前操作fingerprintなど、将来の受理結果へ影響する監査状態を含む。操作ログ自体は含めない。

Undo後に同じ施工または見送りを行った場合、盤面、水流trace、評価材料は元の実行と一致する。action ID、revision、full state hash、ログentryは新しい値になる。

## 浸水、勝敗、評価

### 浸水集約

雨適用直後と、M1の各`FlowStepResult`が返す保護対象超過を、M2が全手番にわたり集約する。雨直後に浸水し、最初の固定ステップの排水で解消した場合も被害として保持する。雨直後の観測点は、その時点で完了済みの絶対水流ステップ番号を使用する。

- `firstFloodStep`: 最初に浸水が発生した絶対水流ステップ。未発生ならnull。
- `peakProtectedOverflow`: 雨直後またはいずれか1固定ステップにおける保護対象超過量合計の最大値。

同じ水が複数固定ステップ残った場合に、超過量を毎回累積加算して被害を水増ししない。水量収支へ浸水量を加えない。必要な原因表示には各固定ステップのtraceを利用する。

安全排水と危険流出はM1の累計counterから開始時との差分を求める。排水能力超過は、各固定ステップの作業用盤面と排水結果から正規順で集約し、最終盤面だけから推測しない。

### 勝敗

一度開始した水流フェーズは、ステージ定義の固定ステップ数を最後まで計算してから評価する。途中で失敗条件へ達しても水流計算を省略しない。

同じ評価時点でクリア条件と失敗条件の両方を満たした場合は、失敗を優先する。判定順は次のとおりとする。

1. 失敗条件
2. 主要目的の達成とステージ終了条件
3. 継続

### 整数3軸評価

評価は検証済みステージ定義と確定済み状態だけから求める純粋な整数計算とする。

- 安全: 0～50
- 工事効率: 0～30
- 流量制御: 0～20
- 合計: 0～100

M2の初期式を次で固定する。`clamp`は両端を含む整数範囲へ収め、割り算は明記した方向へ丸める。

- 安全: `clamp(50 - 危険流出×2 - セル別最大浸水量の合計×5, 0, 50)`
- 工事効率: `clamp(30 - max(0, 変更セル数 - parWork)×4, 0, 30)`
- 流量制御の基礎点: `floor(min(目的別制御量, controlTarget)×20 / controlTarget)`
- 排水能力超過ペナルティ: `ceil(min(最大能力超過量, controlTarget)×20 / controlTarget)`
- 流量制御: `clamp(基礎点 - 排水能力超過ペナルティ, 0, 20)`

目的別制御量は、貯水目的では貯水mask上の現在水量、安全排水目的では累計安全排水量、保護目的では浸水0の場合の処理済み雨量とする。保護目的の`target`は、無被害で通過すべき雨イベント数を表す。どの目的も最大手数の全固定ステップ完了後に主要目的を判定する。

乗算、加算の前後で安全な整数範囲を検査し、浮動小数点の状態値、実時間、描画時間を評価へ使わない。除算結果だけを上記の規則で整数へ丸める。

S／A／B／Cの閾値はステージデータとして整数で持ち、`S > A > B > C`の順序と0～100の範囲をvalidatorで確認する。同じ入力でより多い危険流出または最大浸水が安全評価を上げず、より多い不要工事が工事効率を上げない単調性をテストする。

## StageReplayV1

`StageReplayV1`は最低限次を持つ。

- `version: nagashimasu-stage-replay-v1`
- ステージルール版と水流ルール版
- ステージID、ステージデータ版、definition digest
- 思考時間設定など、ゲーム進行に関係する初期セッション設定
- 初期full state hash
- 受理済み高レベル操作entryの正規順配列

各entryは連続するsequence、高レベル操作、before full state hash、after full state hashを持つ。無効操作、stale操作、同一操作の再送はentryへ追加しない。

再生時は検証済みStageDefinitionから初期状態を再構築し、header、版、digest、初期hashを検査する。その後、操作を順番に再実行し、各before／after hashを一致させる。低レベルの地形、雨、水流命令を記録から直接適用しない。

最大手数64、Undo 1回のMVPでは、受理済みentryを最大66件とする。再生入力は全entryを実行する前に件数、操作payload、sequence、ID、revision、hash形式を検証する。

保存形式を実装するときはStageReplayと別のschema versionを持たせる。中断状態をsnapshotとして保存する場合も、可能な範囲で高レベル操作列を再実行し、保存snapshotとfull state hashを照合する。

## M1を壊さない境界

M2では次を変更しない。

- `WATER_RULES_VERSION`と`REPLAY_LOG_VERSION`
- M1の`SimulationCommand`と`OperationLogEntry`の意味
- 水流係数、走査順非依存規則、水量収支
- `BoardSnapshot`の必須field、直列化順、`hashBoardSnapshot`の結果
- M1の再生上限と検証順

M2は新しい型、validator、reducer、StageReplayを追加する。M1の水流結果に追加の表示証拠が必要な場合は、既存結果の意味を変えず、M2側の派生traceまたは明示的に版管理した追加型で表現する。

## 停止条件

### 操作を確定しない条件

次のいずれかを検出した場合、その操作を補正して続行せず、元状態とログを不変のまま拒否する。

- StageDefinition、パーツ、再生記録の版、digest、型、参照、上限が不正
- action ID、expected revision、sequence、before／after hashが不一致
- 違法フェーズ、使用済みUndo、欠損または不整合なcheckpoint
- 盤外、施工禁止、重複セル、地形上限・下限を越える配置
- 候補列または雨列が定義どおり供給できない
- 雨、水流、評価の途中で安全な整数範囲を越える
- M1の水量収支、走査順、セル範囲、ルール版の不変条件違反
- Undo後のreversible gameplay hashがcheckpointと一致しない
- 再生後のfull state hashが記録と一致しない
- 無制限設定でのタイムアウト、または古いタイマーcallback

### M2 Draft PRを進めない条件

次を満たさない変更はM2完了として扱わず、Ready化しない。

- 施工、雨、水流、評価の途中失敗で全状態がrollbackされるテスト
- confirmとtimeoutの競合、二重タップ、再送、ID衝突、stale操作のテスト
- 候補の持ち越し、使用側だけの補充、見送り時の非補充テスト
- Undoで盤面、水収支、候補、雨、評価、乱数、勝敗が復元されるテスト
- StageReplayのJSON往復、版・digest・hash改変、過大入力拒否テスト
- 最大浸水、失敗優先、評価境界と単調性のテスト
- 描画なしでステージ1～3を完走する統合テスト
- M1の全テスト、型検査、本番build、生成物smoke testの継続成功
