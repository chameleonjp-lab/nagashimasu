# ADR 0009: 結果フィードバック

## 状態

Accepted／M4実装中

## 背景

結果画面にはスコアと失敗理由があるが、失敗後にどこから見直せばよいか、クリア後に何を伸ばせるかが一目で分からない。計画書の「最初に破綻した場所」「主原因の1文」「次に改善する1点」を、既存のStageSession情報から安全に表示する必要がある。

## 決定

- 結果画面は、StageSession snapshotの`failureReasons`、`metrics.firstFloodStep`、`metrics.firstFloodStepByCell`、`score`だけを入力にする。
- 失敗時は、保護対象の初回浸水セルが記録されていればセル番号を表示する。危険側の出口はDomainにセル位置を持たないため、位置を推測せず「危険側の出口」と表示する。
- 失敗理由は一文の原因へまとめ、失敗理由に対応する行動ヒントを1つだけ表示する。
- クリア時は安全、流量制御、工事効率の順に未最大の軸を1つ選び、次の改善点として表示する。すべて最大の場合も、同じ安全を少ない工事で再現する一般的な目標を表示する。
- 変換はPresentationの純粋関数とし、水流計算、クリア判定、スコア、Replay、保存値を変更しない。
- 再生中は既存の結果パネルロックを維持し、再生完了後だけ結果フィードバックと1タップ再挑戦を表示する。

## 禁止事項

- 結果フィードバックのために水流を再実行したり、スコアを再計算したりしない。
- Domainに存在しない危険側のセル、時刻、原因を推測して表示しない。
- 失敗時に複数の改善指示を並べ、次の一手を曖昧にしない。
- 既存の失敗理由や評価配点を表示層から変更しない。

## 検証

- 保護セル、危険側、目的未達、複数理由、クリア時の低い評価軸、全軸最大の各変換を単体テストする。
- 画面ビルドのsmokeで`result-hint`と「次に改善する1点」の組み込みを確認する。
- オンラインランキングは結果画面で折りたたみ、原因・改善点・再挑戦を先に読める順番にする。
- 既存の型検査、全単体テスト、ドメイン／画面build・smokeを通す。
